# Rate Limiting Bypass - Password Reset Environment

## Summary

I identified a Rate Limiting Bypass vulnerability in the password reset environment at `koko-reset.kzlabs.in`.

The application processes password reset requests without implementing proper rate limiting or request throttling mechanisms. By using a brute-force attack with sequential numeric payloads (0 through 7), an attacker can send multiple password reset requests to the server without being blocked or rate-limited. Most requests return a `302 Found` status code (with one returning `202 Accepted`), confirming that the rate limiting mechanism is either not implemented or easily bypassed.

This vulnerability allows attackers to flood the server with password reset requests, potentially leading to denial of service (DoS), resource exhaustion, or bypass of security controls.

## Vulnerability Type

**Rate Limiting Bypass / Password Reset Abuse**

## Vulnerable Parameter

```text
Payload (numeric values)
```

## Vulnerable URL

```text
https://koko-reset.kzlabs.in/index.php
```

## Steps to Reproduce

1. Navigate to the vulnerable password reset page.

2. Intercept a request using Burp Suite, OWASP ZAP, or a similar proxy tool.

3. Send the request to Intruder (Burp Suite) or similar brute-force tool.

4. Configure the attack with sequential numeric payloads (e.g., 0, 1, 2, 3, 4, 5, 6, 7).

5. Launch the attack.

6. Observe that all requests return a `302 Found` or `202 Accepted` status code, indicating that rate limiting is not being enforced.

## Payloads Used

```text
Numeric: 0, 1, 2, 3, 4, 5, 6, 7
```

## Proof of Concept

The application sends a request to the server with a payload parameter:

```http
POST /index.php HTTP/2
Host: koko-reset.kzlabs.in
Content-Type: application/x-www-form-urlencoded

payload=0
```

The server responds with a `302 Found` or `202 Accepted` status code for all requests:

```http
HTTP/2 302 Found
Date: Tue, 25 Aug 2026 16:10:54 GMT
Content-Type: text/html; charset=UTF-8
Location: /reset.php
Server: cloudflare
X-Powered-By: PHP/8.2.33
```

All 8 requests in the attack returned `302 Found` or `202 Accepted`:

| Request | Payload | Status Code | Length |
|---|---|---|---|
| 0 | 0 | 302 | 799 |
| 1 | 1 | 302 | 801 |
| 2 | 2 | 302 | 791 |
| 3 | 3 | 302 | 797 |
| 4 | 4 | 302 | 795 |
| 5 | 5 | 302 | 798 |
| 6 | 6 | 302 | 796 |
| 7 | 7 | 202 | 703 |

This confirms that the rate limiting mechanism is either not implemented or easily bypassed.

## Impact

This Rate Limiting Bypass vulnerability allows an attacker to:

- Perform denial of service (DoS) attacks on the server
- Exhaust server resources (CPU, memory, database connections)
- Flood users' email inboxes with password reset requests
- Bypass anti-brute-force protections
- Potentially discover other vulnerabilities through fuzzing
- Consume bandwidth and network resources

## Recommendation

To mitigate this vulnerability:

### Server-Side Rate Limiting for Password Reset
```php
$ip = $_SERVER['REMOTE_ADDR'];
$email = $_POST['email'] ?? '';
$key = "reset_rate_limit:$ip:$email";
$attempts = redis_get($key);
if ($attempts > 5) {
    http_response_code(429);
    return "Too many reset attempts. Please try again later.";
}
redis_incr($key, 3600); // Increment and expire after 1 hour
```

### IP-Based Throttling
```php
$ip = $_SERVER['REMOTE_ADDR'];
$key = "ip_reset_limit:$ip";
$attempts = redis_get($key);
if ($attempts > 10) {
    http_response_code(429);
    return "Too many reset attempts from this IP.";
}
redis_incr($key, 3600); // Increment and expire after 1 hour
```

### Email-Based Throttling
```php
$email = $_POST['email'] ?? '';
$key = "email_reset_limit:$email";
$attempts = redis_get($key);
if ($attempts > 5) {
    http_response_code(429);
    return "Too many reset attempts for this email.";
}
redis_incr($key, 3600); // Increment and expire after 1 hour
```

### Additional Recommendations

- **CAPTCHA Implementation**: Implement CAPTCHA after a certain number of reset attempts.
- **Progressive Delays**: Implement increasing delays between reset attempts.
- **Logging and Monitoring**: Log all reset attempts and monitor for anomalies.
- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block request flooding.
- **Rate Limiting Headers**: Implement `X-RateLimit-*` headers to inform clients of limits.
- **IP Blacklisting**: Blacklist IPs that exceed the rate limit.
- **Regular Security Audits**: Conduct regular assessments to identify and fix vulnerabilities.
- **Intrusion Detection System (IDS)**: Deploy IDS to detect abnormal traffic patterns.
