# Rate Limiting Bypass - API Testing Environment

## Summary

I identified a Rate Limiting Bypass vulnerability in the API testing environment at `koko-rl-testing.kzlabs.in`.

The application is designed to test rate limiting mechanisms but fails to properly enforce restrictions on the number of requests per session or IP address. By using a brute-force attack with sequential numeric payloads, an attacker can send multiple requests to the server without being blocked or rate-limited.

An attacker can send thousands of requests in a short period, potentially leading to denial of service (DoS), resource exhaustion, or bypass of security controls.

## Vulnerability Type

**Rate Limiting Bypass / Resource Exhaustion**

## Vulnerable Parameter

```text
Payload (numeric values in request body)
```

## Vulnerable URL

```text
https://koko-rl-testing.kzlabs.in/index.php
```

## Steps to Reproduce

1. Navigate to the vulnerable API testing page.

2. Intercept a request using Burp Suite, OWASP ZAP, or a similar proxy tool.

3. Send the request to Intruder (Burp Suite) or similar brute-force tool.

4. Configure the attack with sequential numeric payloads (e.g., 1, 2, 3, 4, 5, 6, 7).

5. Launch the attack.

6. Observe that all requests return a `200 OK` status code, indicating that the rate limit is not being enforced.

## Payloads Used

```text
Numeric: 1, 2, 3, 4, 5, 6, 7, ...
Alphabetical: a, b, c, d, e, ...
Random: random strings
```

## Proof of Concept

The application sends a POST request to the server with a payload parameter:

```http
POST /index.php HTTP/2
Host: koko-rl-testing.kzlabs.in
Cookie: PHPSESSID=d42fe87b4c7777c04dad3d13f0beff62
Content-Type: application/x-www-form-urlencoded

payload=1
```

The server responds with a `200 OK` status code for all requests:

```http
HTTP/2 200 OK
Date: Tue, 25 Aug 2026 15:26:25 GMT
Content-Type: text/html; charset=UTF-8
Server: Cloudflare
X-Powered-By: PHP/8.2.33
Cache-Control: no-store, no-cache, must-revalidate
```

All 7 requests in the attack returned `200 OK`:

| Request | Payload | Status Code | Length |
|---|---|---|---|
| 0 | 1 | 200 | 16011 |
| 1 | 2 | 200 | 16009 |
| 2 | 3 | 200 | 16020 |
| 3 | 4 | 200 | 16019 |
| 4 | 5 | 200 | 16017 |
| 5 | 6 | 200 | 16012 |
| 6 | 7 | 200 | 16014 |

This confirms that the rate limiting mechanism is either not implemented or easily bypassed.

## Impact

This Rate Limiting Bypass vulnerability allows an attacker to:

- Perform denial of service (DoS) attacks on the server
- Exhaust server resources (CPU, memory, database connections)
- Bypass anti-brute-force protections
- Perform credential stuffing attacks without being blocked
- Flood the application with malicious requests
- Potentially discover other vulnerabilities through fuzzing

## Recommendation

To mitigate this vulnerability:

- **Server-Side Rate Limiting**: Implement rate limiting on the server side using a database or cache.
  ```php
  $ip = $_SERVER['REMOTE_ADDR'];
  $sessionId = session_id();
  $key = "rate_limit:$ip:$sessionId";
  $attempts = redis_get($key);
  if ($attempts > 10) {
      http_response_code(429);
      return "Too many requests. Please try again later.";
  }
  redis_incr($key, 60); // Increment and expire after 1 minute
  ```

- **IP-Based Throttling**: Implement rate limiting based on IP address.

- **Session-Based Throttling**: Track and limit requests per session.

- **CAPTCHA Implementation**: Implement CAPTCHA after a certain number of attempts.

- **Exponential Backoff**: Implement increasing delays between failed attempts.

- **Request Validation**: Validate request parameters to filter out malicious payloads.

- **Logging and Monitoring**: Log all requests and monitor for anomalies.

- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block malicious traffic.

- **Regular Security Audits**: Conduct regular assessments to identify and fix vulnerabilities.
