# Stored HTML Injection - Profile Settings & Email Invitations

## Summary

I identified a Stored HTML Injection vulnerability in the Profile Settings of the Romit wallet application.

The application accepts user-controlled input through the **Nickname** field and stores it in the database without proper sanitization or output encoding. The injected HTML is rendered in multiple locations: the user's profile settings, the wallet sharing interface, and most critically, the recipient email preview. By injecting `<h1>` tags with inline styles, an attacker can manipulate the visual appearance of the page and email content sent to recipients.

An attacker can update their nickname with malicious HTML that, when viewed by other users or when wallet invitations are sent, renders arbitrary HTML within the trusted application context. This can be used for phishing attacks, defacement, or social engineering of wallet recipients.

## Vulnerability Type

**HTML Injection (Stored)**

## Vulnerable Parameter

```text
Nickname
```

## Vulnerable URL

```text
https://kzlabs.in/1203.php?save=1#settings
```

## Steps to Reproduce

1. Navigate to the vulnerable profile settings page.

2. Update the **Nickname** field with the following payload:

   ```text
   <h1 style="color:red">HACKED</h1>
   ```

3. Click the **Save Changes** button.

4. Observe that the nickname is saved and displayed on the settings page.

5. Navigate to the **Share Your Wallet** section.

6. Observe that the injected HTML appears in the "Your current nickname" field.

7. Preview the recipient email notification.

8. Observe that the injected HTML is rendered in the email preview with red "HACKED" text.

## Payload Used

```text
<h1 style="color:red">HACKED</h1>
```

URL-encoded version:
```text
%3Ch1%20style%3D%22color%3Ared%22%3EHACKED%3C%2Fh1%3E
```

## Proof of Concept

The application accepts the value of the Nickname field and stores it in a database without proper sanitization. When displayed in multiple contexts, the user-controlled input is rendered directly into the HTML.

The payload works by:
1. Injecting an HTML heading tag (`<h1>`) with an inline style attribute
2. The browser renders the injected HTML in the settings page
3. The same injected HTML appears in the wallet sharing interface
4. The HTML is also rendered in the recipient email preview

```html
<!-- Injected payload rendered in the page: -->
<h1 style="color:red">HACKED</h1>
```

The payload is stored in the database and rendered in:
- Profile Settings page
- Share Your Wallet section
- Recipient email notifications

## Impact

Stored HTML Injection vulnerabilities in profile settings are particularly dangerous because:

- **Persistent**: Malicious HTML is permanently stored in the database
- **Multiple Contexts**: The payload is rendered in multiple locations
- **Email Propagation**: Payloads are sent to recipients via email
- **Phishing**: Attackers can inject fake forms or misleading content in emails
- **Brand Damage**: Defacement of trusted application pages and emails

An attacker can:

- Inject phishing links into email notifications sent to wallet recipients
- Deface the user's profile and sharing interface
- Create convincing fake messages or alerts in emails
- Redirect users to malicious websites via injected links
- Damage brand reputation and user trust

## Recommendation

To mitigate this vulnerability:

- **Output Encoding**: Use `htmlspecialchars()` (or an equivalent output-encoding function) before rendering user-controlled data in HTML for ALL contexts.
  ```php
  echo htmlspecialchars($nickname, ENT_QUOTES, 'UTF-8');
  ```

- **Email Sanitization**: Ensure email content is properly sanitized before being sent.
  ```php
  $emailBody = strip_tags($nickname);
  ```

- **Input Validation**: Validate and sanitize all user inputs before storing. Consider using a whitelist approach to allow only safe characters.
  ```php
  $nickname = preg_replace('/[^a-zA-Z0-9\s\-_.]/', '', $_POST['nickname']);
  ```

- **HTML Sanitization**: Use a robust HTML sanitization library (like DOMPurify or HTML Purifier) to strip dangerous tags and attributes.

- **Content Security Policy (CSP)**: Implement a strict CSP to restrict inline styles and unauthorized content.

- **Email Content Security**: Send emails in plain text or use strict HTML filtering for email content.

- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block malicious HTML payloads.

- **Security Headers**: Implement security headers like `X-XSS-Protection` and `X-Content-Type-Options` for additional protection.

- **Regular Security Audits**: Conduct regular assessments and code reviews to identify vulnerabilities.
