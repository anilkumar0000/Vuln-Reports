# Stored HTML Injection in Support Chat System

## Summary

I identified a Stored HTML Injection vulnerability in the Support Chat System of the application.

The application accepts user-controlled input through the chat/message field and stores it in the database without proper sanitization or output encoding. When support agents view the incoming messages in their inbox, the injected HTML is rendered and interpreted by the browser. By injecting a `<a>` tag with a `href` attribute pointing to a malicious external site, an attacker can create phishing links that appear legitimate within the support agent's interface.

An attacker can send a support message containing malicious HTML that, when viewed by support staff, renders as a legitimate clickable link. This could be used to trick support agents into visiting malicious websites, potentially leading to credential theft, session hijacking, or further compromise of internal systems.

## Vulnerability Type

**HTML Injection (Stored)**

## Vulnerable Parameters

```text
Message field
Support Chat Input
```

## Vulnerable URL

```text
https://kzlabs.in/70.php (Assumed based on lab progression)
```

## Steps to Reproduce

1. Navigate to the support chat page.

2. Enter the following payload in the chat/message field:

   ```text
   <a href="evil.com">Click here for support documentation</a>
   ```

3. Submit the message.

4. The message is stored in the database and appears in the support agent's inbox.

5. The support agent sees the message with a clickable link that appears legitimate.

6. The link points to `evil.com` or any attacker-controlled domain.

## Payloads Used

```text
<a href="evil.com">Click here for support documentation</a>
<a href="https://attacker.com/phishing">Login to view ticket</a>
<a href="javascript:alert(1)">Click me</a> (Escalation to XSS)
```

## Proof of Concept

The support chat system accepts user input and stores it in a database without proper sanitization. When support agents view incoming messages, the user-controlled HTML is rendered directly into the page.

The payload works by:
1. Injecting an HTML anchor tag (`<a>`) with a malicious `href` attribute
2. The link appears as a legitimate clickable link in the agent's inbox
3. When clicked, the agent is redirected to the attacker-controlled domain
4. This can be used for phishing attacks targeting support staff

```html
<!-- Injected payload rendered in the page: -->
<a href="evil.com">Click here for support documentation</a>
```

The risk is particularly high because:
- Support agents are trusted users with elevated privileges
- They are trained to click links in support tickets to access documentation
- The link appears within a trusted application context

## Impact

HTML Injection vulnerabilities in support chat systems are particularly dangerous because:

- **Phishing Support Staff**: Attackers can trick support agents into visiting malicious websites
- **Credential Theft**: Agents may enter their credentials on fake login pages
- **Session Hijacking**: Stolen session cookies can be used to access internal systems
- **Internal Network Access**: Support agents often have access to internal tools and networks
- **Trusted Context**: Links appear within the application, making them seem legitimate

An attacker can:

- Steal support agent credentials via phishing links
- Hijack support agent sessions
- Access internal support tools and systems
- View sensitive customer data
- Escalate to XSS with more advanced payloads

## Recommendation

To mitigate this vulnerability:

- **HTML Sanitization**: Use a robust HTML sanitization library (like DOMPurify or HTML Purifier) to strip dangerous tags and attributes.
  ```javascript
  // Client-side
  const cleanMessage = DOMPurify.sanitize(message);
  ```

  ```php
  // Server-side
  $cleanMessage = HTMLPurifier::sanitize($_POST['message']);
  ```

- **Output Encoding**: Use `htmlspecialchars()` (or an equivalent output-encoding function) before rendering user-controlled data.
  ```php
  echo htmlspecialchars($message, ENT_QUOTES, 'UTF-8');
  ```

- **Input Validation**: Validate and sanitize all user inputs before storing. Consider using a whitelist approach to allow only safe content.

- **Content Security Policy (CSP)**: Implement a strict CSP that restricts navigation to unauthorized domains.

- **Link Warning**: Display a warning when users click on external links from support messages.

- **Context-Aware Escaping**: Use appropriate escaping based on where the data is placed (HTML body, attributes, etc.).

- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block malicious HTML payloads.

- **Security Headers**: Implement security headers like `X-XSS-Protection`, `X-Content-Type-Options`, and other security headers.

- **Regular Security Audits**: Conduct regular assessments and code reviews to identify vulnerabilities.

- **Staff Training**: Educate support staff about the risks of clicking links in support tickets.
