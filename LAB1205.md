# Stored HTML Injection - HackerOne Pentest Community Application

## Summary

I identified a Stored HTML Injection vulnerability in the HackerOne Pentest Community Application form.

The application accepts user-controlled input through multiple form fields (First Name, Last Name, HackerOne Handle, and Why do you want to join?) and stores them in the database without proper sanitization or output encoding. When the application sends confirmation emails to applicants or displays the application data, the injected HTML is rendered and interpreted by the browser. By injecting HTML tags such as `<h1>` with inline styles, an attacker can manipulate the visual appearance of both the application page and email notifications sent to recipients.

An attacker can submit an application with malicious HTML in the form fields that, when viewed by administrators or when confirmation emails are sent, renders arbitrary HTML within the trusted application and email context. This can be used for phishing attacks, defacement, or social engineering of administrators and recipients.

## Vulnerability Type

**HTML Injection (Stored)**

## Vulnerable Parameters

```text
First Name
Last Name
HackerOne Handle
Why do you want to join?
```

## Vulnerable URL

```text
https://kzlabs.in/1205.php?view=pentest-application (Assumed based on lab progression)
```

## Steps to Reproduce

1. Navigate to the vulnerable Pentest Community Application page.

2. Fill in the application form with the following payloads:

   - **First Name**: `<h1 style="color:red">HACKER1</h1>`
   - **Last Name**: `<h1 style="color:red">HACKER2</h1>`
   - **HackerOne Handle**: `<h1 style="color:red">HACKED</h1>`
   - **Why do you want to join?**: `<h1 style="color:red">HACKER4</h1>`

3. Fill in other required fields (Email, Experience, Specialties, LinkedIn Profile).

4. Click the **Submit Application** button.

5. Observe that the application is submitted and stored in the database.

6. Check the confirmation email preview or the admin dashboard.

7. Observe that the injected HTML is rendered by the browser, displaying "HACKER1", "HACKER2", "HACKED", and "HACKER4" in red text.

## Proof of Concept

The application accepts the values of the form fields and stores them in a database without proper sanitization. When applications are displayed or confirmation emails are sent, the user-controlled input is rendered directly into the HTML.

The payload works by:
1. Injecting HTML heading tags (`<h1>`) with inline style attributes
2. The browser renders the injected HTML within the page
3. The same injected HTML appears in confirmation emails sent to recipients

```html
<!-- Injected payload rendered in the page and email: -->
<h1 style="color:red">HACKER1</h1>
<h1 style="color:red">HACKER2</h1>
<h1 style="color:red">HACKED</h1>
<h1 style="color:red">HACKER4</h1>
```

The parameters are clearly identified in the HTML source:
```html
<!-- Parameter: first_and_last_name[first] -->
<!-- Parameter: first_and_last_name[last] -->
```

## Impact

Stored HTML Injection vulnerabilities in application forms are particularly dangerous because:

- **Persistent**: Malicious HTML is permanently stored in the database
- **Email Propagation**: Payloads are rendered in confirmation emails sent to applicants
- **Trusted Context**: Emails come from a trusted domain (HackerOne)
- **Phishing**: Attackers can inject fake links or forms in email notifications
- **Brand Damage**: Defacement of trusted application pages and emails

An attacker can:

- Inject phishing links into email notifications sent to applicants
- Deface the application submission page
- Create convincing fake messages or alerts in emails
- Manipulate content to mislead administrators
- Damage brand reputation and user trust

## Recommendation

To mitigate this vulnerability:

- **Output Encoding**: Use `htmlspecialchars()` (or an equivalent output-encoding function) before rendering user-controlled data in HTML for ALL contexts.
  ```php
  echo htmlspecialchars($firstName, ENT_QUOTES, 'UTF-8');
  echo htmlspecialchars($lastName, ENT_QUOTES, 'UTF-8');
  echo htmlspecialchars($handle, ENT_QUOTES, 'UTF-8');
  echo htmlspecialchars($reason, ENT_QUOTES, 'UTF-8');
  ```

- **Email Sanitization**: Ensure email content is properly sanitized before being sent.
  ```php
  $emailBody = strip_tags($firstName . ' ' . $lastName);
  ```

- **Input Validation**: Validate and sanitize all user inputs before storing. Consider using a whitelist approach to allow only safe characters.
  ```php
  $firstName = preg_replace('/[^a-zA-Z0-9\s\-_.]/', '', $_POST['firstName']);
  ```

- **HTML Sanitization**: Use a robust HTML sanitization library (like DOMPurify or HTML Purifier) to strip dangerous tags and attributes.

- **Content Security Policy (CSP)**: Implement a strict CSP to restrict inline styles and unauthorized content.

- **Email Content Security**: Send emails in plain text or use strict HTML filtering for email content.

- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block malicious HTML payloads.

- **Security Headers**: Implement security headers like `X-XSS-Protection`, `X-Content-Type-Options`, and other security headers.

- **Regular Security Audits**: Conduct regular assessments and code reviews to identify vulnerabilities.
