# Stored HTML Injection - GitLab Profile Settings

## Summary

I identified a Stored HTML Injection vulnerability in the GitLab Profile Settings of the application.

The application accepts user-controlled input through multiple profile fields (Full Name, Username, Bio) and stores them in the database without proper sanitization or output encoding. When users view the profile page or snippet pages, the injected HTML is rendered and interpreted by the browser. By injecting HTML tags such as `<h1>` with inline styles, an attacker can manipulate the visual appearance of profile pages and other public areas.

An attacker can update their profile with malicious HTML that, when viewed by other users, renders arbitrary HTML within the trusted application context. This can be used for defacement, phishing attacks, or social engineering of other users.

## Vulnerability Type

**HTML Injection (Stored)**

## Vulnerable Parameters

```text
Full Name
Username
Bio
```

## Vulnerable URL

```text
https://kzlabs.in/1204.php?view=settings
```

## Steps to Reproduce

1. Navigate to the vulnerable profile settings page at `https://kzlabs.in/1204.php?view=settings`.

2. Update the following profile fields with HTML payloads:

   - **Full Name**: `<h1 style="color:red">HACKER</h1>`
   - **Username**: `<h1 style="color:red">HACKER</h1>`
   - **Bio**: `<h1 style="color:red">ROBBED</h1>`

3. Click the **Update Profile Settings** button to save the changes.

4. Navigate to the public profile or snippet page.

5. Observe that the injected HTML is rendered by the browser, displaying "HACKER" and "ROBBED" in red text.

## Payloads Used

```text
Full Name: <h1 style="color:red">HACKER</h1>
Username: <h1 style="color:red">HACKER</h1>
Bio: <h1 style="color:red">ROBBED</h1>
```

URL-encoded versions:
```text
Full Name: %3Ch1%20style%3D%22color%3Ared%22%3EHACKER%3C%2Fh1%3E
Username: %3Ch1%20style%3D%22color%3Ared%22%3EHACKER%3C%2Fh1%3E
Bio: %3Ch1%20style%3D%22color%3Ared%22%3EROBBED%3C%2Fh1%3E
```

## Proof of Concept

The application accepts the values of the profile fields and stores them in a database without proper sanitization. When profiles or snippet pages are displayed, the user-controlled input is rendered directly into the page HTML.

The payload works by:
1. Injecting HTML heading tags (`<h1>`) with inline style attributes
2. The browser renders the injected HTML within the page

```html
<!-- Injected payload rendered in the page: -->
<h1 style="color:red">HACKER</h1>
```

The payload is persistently stored and executed every time a user views the profile or snippet pages.

## Impact

Stored HTML Injection vulnerabilities in profile settings are dangerous because:

- **Persistent**: Malicious HTML is permanently stored in the database
- **Widespread Impact**: All users viewing profiles or snippets are affected
- **No User Interaction Required**: Victims don't need to click a malicious link
- **Phishing**: Attackers can inject fake forms or misleading content
- **Defacement**: Visual manipulation of trusted application pages

An attacker can:

- Deface the user's profile and snippet pages
- Inject phishing links into profile fields
- Create convincing fake messages or alerts
- Manipulate page content to mislead users
- Damage brand reputation and user trust

## Recommendation

To mitigate this vulnerability:

- **Output Encoding**: Use `htmlspecialchars()` (or an equivalent output-encoding function) before rendering user-controlled data in HTML.
  ```php
  echo htmlspecialchars($fullName, ENT_QUOTES, 'UTF-8');
  echo htmlspecialchars($username, ENT_QUOTES, 'UTF-8');
  echo htmlspecialchars($bio, ENT_QUOTES, 'UTF-8');
  ```

- **Input Validation**: Validate and sanitize all user inputs before storing. Consider using a whitelist approach to allow only safe characters.
  ```php
  $fullName = preg_replace('/[^a-zA-Z0-9\s\-_.]/', '', $_POST['fullName']);
  ```

- **HTML Sanitization**: Use a robust HTML sanitization library (like DOMPurify or HTML Purifier) to strip dangerous tags and attributes.

- **Content Security Policy (CSP)**: Implement a strict CSP to restrict inline styles and unauthorized content.

- **Context-Aware Escaping**: Use appropriate escaping based on where the data is placed (HTML body, attributes, JavaScript).

- **Web Application Firewall (WAF)**: Deploy a WAF to detect and block malicious HTML payloads.

- **Security Headers**: Implement security headers like `X-XSS-Protection`, `X-Content-Type-Options`, and other security headers.

- **Regular Security Audits**: Conduct regular assessments and code reviews to identify vulnerabilities.
